# x-japanese-writing-reviewのテスト

このスキルを変更したPRは、ここにあるテストが全件合格していないとマージできません。テストはローカルで実行し、結果の`results.json`をコミットします。CIの`writing-review-tests`ワークフローは、LLMを呼ばずに`results.json`を検査します。

## テストの単位

テストの単位はルールファイル（`rule-*.md`）です。ルールファイルごとに、`rules/<ルールファイル名>/`へ次の2つのファイルを置きます。

- `input.md`：テストされるエージェントに渡す文書そのものです。ケースは`<!-- case:ID -->`の行で区切ります
- `expected.md`：ケースごとの事前の定義です。テストされるエージェントには渡しません

ランナーは、`input.md`を1つの`claude -p`セッションに渡し、SKILL.mdの手順で検知と修正をさせます。SKILL.mdの手順と異なる点は次の3つです。

- 使うルールファイルは、テストするファイルだけです
- 周回数は2回です。テストの文書は50〜140行と短いためです
- ユーザーに確認できないので、文書を書いた作業のコンテキストを`context.md`として渡し、会話の代わりに読ませます

テストされるエージェントには、SKILL.md・対象のルールファイル・`methods/*.md`だけを一時ディレクトリにコピーして読ませます。スキルのディレクトリ全体を読ませると、`expected.md`を読めてしまうためです。ルールファイルごとに別のセッションで実行するので、ほかのルールファイルのケースや結果は判定に影響しません。6つのルールファイルの指摘を統合する工程（SKILL.mdの手順2）は、テストしません。

## 判定のしかた

テストでは、文書を書いた作業のコンテキストを、テストされるエージェントに最初から渡します。通常は、文書を書いた作業の中でスキルを使うためです（ユーザー判断、2026-10-19）。あとから別のコンテキストで改善する場合の流れ（保留する → ユーザーに質問する → 回答をもとに直す）は、テストしません。

修正の正解を1つの文に固定しません。表現の揺れを許し、結果がルールに沿っているかで判定します。

次の4つはスクリプトで判定します。解釈の余地がないためです。

- 検知：「検知する文」が、対象のルールの違反として指摘されたか
- 変えない文：「変えない文」が指摘されず、原文のまま残っているか
- 数値：元の文書にない数値が増えていないか。項目数と、箇条書きの番号は除きます
- 修正：検知した違反を直したか。すべてのケースはコンテキストを使えば直せる違反なので、保留も不合格にします

修正の質は、判定エージェント（`opus`）が判定します。判定エージェントは`expected.md`の定義を読んだうえで、コンテキストを踏まえて修正前と修正後を比べ、「修正の観点」の1つずつについて判定します。すべての観点を満たした場合だけ合格です。

判定エージェントが誤ると、テストの結果を信用できなくなってしまいます。そのため、判定のテスト（`judge/<ルールファイル名>`）を別に置きます。判定のテストでは、`expected.md`の合格の例と不合格の例を修正後の文書として判定エージェントに渡し、合格の例をすべて合格、不合格の例をすべて不合格と判定できるかを確かめます。判定する例は、判定の参考に渡す例から外します。

校正のテストは`opus`と`sonnet`（実行した時点の最新モデル）で、判定のテストは`opus`で、それぞれ2回ずつ実行します。2回とも全ケースが合格した場合だけ合格です。

## expected.mdの書き方

ケースごとに、`## <ケースID>`の見出しの下へ次の項目を書きます。

ランナーは、次のどれかに当てはまるとエラーで止まります。

- 項目が欠けている
- `input.md`とケースが一致しない
- ルールファイルの見出しに対応するケースがない

| 項目 | 内容 |
|---|---|
| `- ルール：` | ルールファイルの見出し（`## `のあとの文字列）と同じ文字列 |
| `- 検知する文：` | 違反として検知されるべき箇所。複数書いた場合は、すべての検知が必要です。1行の中を「｜」で区切ると、そのどれかの検知で合格です |
| `- コードブロックの変更：可` | コードブロックを書き換えるのが正しい修正のケースにだけ書きます |
| `### コンテキスト` | 書き手に聞けばわかる事実（正式名称・出典・基準の数値・方針など）。文書内の情報だけで直せるケースには書きません。直し方そのもの（「〜と書き換える」）は書きません。直し方を書くと、エージェントは手順ではなくその答えに合わせて直してしまうためです |
| `### 変えない文` | 違反ではない文。4つのバッククォートで囲んだ`text`ブロックで書きます |
| `### 誤りの箇所と理由` | どの文のどこが、ルールのどの記述に照らしてなぜ誤りか |
| `### 修正の観点` | 正しい修正なら必ず満たす条件。番号付きの箇条書きで書きます |
| `### 合格の例` | 修正後のセクション全体（`markdown`）。表現の揺れを示すため、2つ以上書きます。ただし、文を削除するだけの修正のように、正しい直し方が1通りに決まるケースは1つにします。判定が人によって分かれる例を2つ目として作ると、判定のテストが不安定になってしまうためです |
| `### 不合格の例` | 不合格の理由を1文書いてから、例を書きます |

例は4つのバッククォートで囲みます。例の中に、3つのバッククォートで囲んだコードブロックを含めることがあるためです。

`input.md`と`expected.md`は`.textlintignore`でtextlintの対象から外しています。どちらにも違反を意図的に書くためです。

## 実行のしかた

```bash
python3 claude/skills/x-japanese-writing-review/tests/run.py run
python3 claude/skills/x-japanese-writing-review/tests/run.py verify
```

`run`は、依存ファイルが変わったテストと、不合格のテストだけを実行します。`--filter`でテストのIDを正規表現で絞り、`--models sonnet`でモデルを絞り、`--all`で全件を再実行します。各回の指摘・校正後の文書・判定の結果は`.logs/`に保存します。`.logs/`はコミットしません。

テストの依存ファイルは次のとおりです。いずれかを変えると、そのテストの結果は古いものとして扱われ、`verify`が失敗します。

- 校正のテスト：`run.py`・SKILL.md・そのルールファイル・`methods/*.md`・`input.md`・`expected.md`
- 判定のテスト：`run.py`・そのルールファイル・`input.md`・`expected.md`

`verify`はLLMを呼ばないので、新しいモデルが出たことを検出できません。新しいモデルでの結果は、次に`run`を実行したときに記録されます。

## ケースを変えるとき

- 期待する結果は、テストを実行する前に決めます。人によって期待が分かれる入力は、ケースに使いません
- 1つのルールファイルのケースは1つの文書に結合されるので、ほかのケースの文から、違反を直す情報を得られないようにします。コンテキストも1つのファイルにまとめて渡します。そのため、あるケースのコンテキストを、別のケースの答えとして使えないようにします
- 変えない文には、同じファイルのどのルールにも違反せず、違反の文が指す先とも読めない文を選びます
- 実行結果を見てからケースを変えた場合は、変えた理由をコミットメッセージに書きます
- Sonnetだけが不合格になった場合は、ケースではなくルールの説明を直します。ルールの説明が、読み手によって複数の意味に解釈できる可能性が高いためです
