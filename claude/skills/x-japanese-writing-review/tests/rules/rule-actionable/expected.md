# rule-actionableのテストの期待結果

## negative-sentence

- ルール：否定文は肯定文に書き換えます
- 検知する文：保護ブランチへ直接pushしません

### コンテキスト

- pushする先は、作業ごとに`main`から作る作業用のブランチです

### 変えない文

````text
保護ブランチは`main`と`release`です。
````

### 誤りの箇所と理由

「保護ブランチへ直接pushしません」が誤りです。この否定文は何をしないかだけを示し、どのブランチへpushすればよいかを示していません。肯定文を補足する否定文でもないので、ルールに従って肯定文に書き換えます。push先が作業用のブランチであることはコンテキストにあるので、その事実を使って直せます。

### 修正の観点

1. push先が肯定文で書かれ、「pushしません」が残っていない
2. コンテキストにある事実（push先は作業用のブランチ）を使って直している
3. 保護ブランチが`main`と`release`であることが、元の文から変わっていない
4. コンテキストにも元の文書にもない特定のブランチ名（`develop`など）を加えていない

### 合格の例

````markdown
## コミット先

作業用のブランチへpushします。

保護ブランチは`main`と`release`です。
````

````markdown
## コミット先

作業ごとに`main`から作った作業用のブランチへpushします。

保護ブランチは`main`と`release`です。
````

### 不合格の例

否定文が残っている。

````markdown
## コミット先

保護ブランチへは直接pushしないでください。

保護ブランチは`main`と`release`です。
````

コンテキストにないブランチ名を作って加えている。

````markdown
## コミット先

`develop`ブランチへpushします。

保護ブランチは`main`と`release`です。
````

## done-criteria

- ルール：完了条件は境界を網羅的・具体的に書きます
- 検知する文：一覧画面の表示が十分に速いこと

### コンテキスト

- 一覧画面は、ブラウザでURLを開いてから2秒以内に表示されれば完了とします

### 変えない文

````text
- `npm run build`が終了コード0で終わること
````

### 誤りの箇所と理由

「一覧画面の表示が十分に速いこと」の「十分に」が誤りです。ルールは「十分な」のような曖昧な形容を観測基準に置き換えるよう求めています。完了とする基準（URLを開いてから2秒以内）はコンテキストにあるので、その基準に置き換えて直せます。2つ目の条件は終了コード0という観測できる状態なので、違反ではありません。

### 修正の観点

1. 「十分に」が残っておらず、観測できる基準で書かれている
2. コンテキストにある基準（ブラウザでURLを開いてから2秒以内）を使って直している
3. コンテキストにも元の文書にもない基準や数値を加えていない
4. 2つ目の条件が元のまま残っている

### 合格の例

````markdown
## リリース

### 完了条件

- 一覧画面が、ブラウザでURLを開いてから2秒以内に表示されること
- `npm run build`が終了コード0で終わること
````

````markdown
## リリース

### 完了条件

- ブラウザで一覧画面のURLを開いてから、2秒以内に一覧画面が表示されること
- `npm run build`が終了コード0で終わること
````

### 不合格の例

曖昧な形容が残っている。

````markdown
## リリース

### 完了条件

- 一覧画面が十分に速く表示されること
- `npm run build`が終了コード0で終わること
````

コンテキストにない数値を作って書き換えている。

````markdown
## リリース

### 完了条件

- 一覧画面が、ブラウザでURLを開いてから1秒以内に表示されること
- `npm run build`が終了コード0で終わること
````

## active-voice

- ルール：読み手がすべきことは、読み手を主体にした能動態で書きます
- 検知する文：ログイン後、パスワードの変更が求められます

### 変えない文

````text
インストーラーを起動してください。必要なパッケージがダウンロードされます。
````

### 誤りの箇所と理由

「パスワードの変更が求められます」が誤りです。パスワードを変更するのは読み手なのに、受動態で書かれているため、読み手は自分が何をすればよいかを判断しにくくなります。ルールに従って、読み手を主体にした能動態で書きます。2文目の「ダウンロードされます」は読み手の行動によって起きる結果なので、受動態のままが正しい書き方です。

### 修正の観点

1. パスワードを変更することが、読み手を主体にした能動態（「変更してください」など）で書かれている
2. ログインの後にパスワードを変更するという順序が、元の文から変わっていない
3. 「必要なパッケージがダウンロードされます」が受動態のまま残っている

### 合格の例

````markdown
## 初回ログイン

ログインしたら、パスワードを変更してください。

インストーラーを起動してください。必要なパッケージがダウンロードされます。
````

````markdown
## 初回ログイン

ログインした後に、パスワードを変更してください。

インストーラーを起動してください。必要なパッケージがダウンロードされます。
````

### 不合格の例

受動態が残っている。

````markdown
## 初回ログイン

ログイン後、パスワードの変更を求められます。

インストーラーを起動してください。必要なパッケージがダウンロードされます。
````

違反ではない2文目まで能動態に書き換えている。

````markdown
## 初回ログイン

ログインしたら、パスワードを変更してください。

インストーラーを起動してください。インストーラーが必要なパッケージをダウンロードします。
````

## subject-predicate

- ルール：主語を省略せず明示し、主語と述語を対応させます
- 検知する文：このhookの役割は、保護ブランチへのコミットを拒否します

### 変えない文

````text
このhookは、拒否したコミットの記録を`hook.log`に書き込みます。
````

### 誤りの箇所と理由

「このhookの役割は、保護ブランチへのコミットを拒否します」が誤りです。主語「役割は」に対して述語が「拒否します」となっており、主語と述語が対応していません。ルールに従って、「役割は〜することです」とするか、主語を「このhookは」にして対応させます。

### 修正の観点

1. 1文目の主語と述語が対応している（「役割は〜ことです」または「このhookは〜拒否します」）
2. hookが保護ブランチへのコミットを拒否することが、元の文から変わっていない
3. 元の文書にない条件を加えていない

### 合格の例

````markdown
## pre-commit hook

このhookの役割は、保護ブランチへのコミットを拒否することです。

このhookは、拒否したコミットの記録を`hook.log`に書き込みます。
````

````markdown
## pre-commit hook

このhookは、保護ブランチへのコミットを拒否します。

このhookは、拒否したコミットの記録を`hook.log`に書き込みます。
````

### 不合格の例

主語と述語が対応していない。

````markdown
## pre-commit hook

このhookの役割は、保護ブランチへのコミットを拒否するようにします。

このhookは、拒否したコミットの記録を`hook.log`に書き込みます。
````

拒否する対象が変わっている。

````markdown
## pre-commit hook

このhookの役割は、すべてのコミットを拒否することです。

このhookは、拒否したコミットの記録を`hook.log`に書き込みます。
````

## object-and-condition

- ルール：動作を述べる文には、動作の対象と条件を書きます
- 検知する文：問題が起きたら戻します

### コンテキスト

- 戻す対象は、本番環境にデプロイしたアプリケーションで、直前のバージョンへ戻します
- 戻すのは、デプロイしてから10分間のエラー率が5%を超えたときです

### 変えない文

````text
保存期間の30日を過ぎたログファイルは、毎日0時に削除します。
````

### 誤りの箇所と理由

「問題が起きたら戻します」が誤りです。何を何の状態へ戻すのかという対象と、どのような問題が起きたら戻すのかという条件が書かれていないので、読み手はこの文から行動を決められません。対象（本番環境のアプリケーションを直前のバージョンへ）と条件（デプロイ後10分間のエラー率が5%を超えたとき）はコンテキストにあるので、その事実を使って直せます。2文目は対象（30日を過ぎたログファイル）と条件（毎日0時）が書かれているので、違反ではありません。

### 修正の観点

1. 戻す対象（本番環境のアプリケーション）と戻し先（直前のバージョン）が書かれている
2. 戻す条件が、コンテキストにある基準（デプロイしてから10分間のエラー率が5%を超えたとき）で書かれ、「問題が起きたら」が残っていない
3. コンテキストにも元の文書にもない対象・条件・数値を加えていない
4. 2文目が元のまま残っている

### 合格の例

````markdown
## 運用

デプロイしてから10分間のエラー率が5%を超えた場合は、本番環境のアプリケーションを直前のバージョンへ戻します。

保存期間の30日を過ぎたログファイルは、毎日0時に削除します。
````

````markdown
## 運用

本番環境にデプロイしたアプリケーションは、デプロイ後10分間のエラー率が5%を超えたら、直前のバージョンへ戻します。

保存期間の30日を過ぎたログファイルは、毎日0時に削除します。
````

### 不合格の例

対象は書いたが、曖昧な条件が残っている。

````markdown
## 運用

問題が起きたら、本番環境のアプリケーションを直前のバージョンへ戻します。

保存期間の30日を過ぎたログファイルは、毎日0時に削除します。
````

コンテキストにない数値を作って条件を書いている。

````markdown
## 運用

デプロイ後にエラー率が1%を超えた場合は、本番環境のアプリケーションを直前のバージョンへ戻します。

保存期間の30日を過ぎたログファイルは、毎日0時に削除します。
````

## test-name

- ルール：テスト名とコードコメントは、ドメインの語と外から観測できる振る舞いで書きます

- `Label`は、在庫がある商品では`null`を返します

### 変えない文

````text
- 編集権限がない利用者には、ボタンを表示しない（`isEditable`が`false`）
````

### 誤りの箇所と理由

「`Label`が`null`を返す」が誤りです。`null`を返すという技術語だけで書かれており、何のための検証かを読み手が理解できません。`null`を返すのは在庫がある商品で「在庫切れ」のラベルを表示しないときであることがコンテキストにあるので、その振る舞いをドメインの語で先に書き、`Label`が`null`を返すことを括弧内に書いて直せます。2つ目のテスト名はルールに沿っています。

### 修正の観点

1. 在庫がある商品では「在庫切れ」のラベルを表示しないという振る舞いが、ドメインの語で先に書かれている
2. `Label`が`null`を返すことが括弧内に残っている
3. コンテキストにも元の文書にもない条件を加えていない
4. 2つ目のテスト名が元のまま残っている

### 合格の例

## external-source

- ルール：外部の事実にもとづく記述には、出典のリンクと引用を添えます
- 検知する文：Node.js 18のサポートは2025年4月30日に終了しました

### コンテキスト

- 出典はNode.jsの公式サイトの「Node.js Releases」（https://nodejs.org/en/about/previous-releases）です
- 該当箇所は、リリースの一覧表のv18の行で、End-of-life列に「2025-04-30」とあります

### 変えない文

````text
次の設定で、Node.js 20以上を必須にしています。
````

### 誤りの箇所と理由

「Node.js 18のサポートは2025年4月30日に終了しました」が誤りです。Node.jsのサポート期限は外部の事実なのに、出典のリンクと引用が添えられていないので、読み手は記述が正しいかを確かめられません。出典のURLと該当箇所はコンテキストにあるので、その事実を使ってリンクと引用を添えて直せます。2文目は文書内の設定で確かめられる記述なので、ルールの例外に当たり、違反ではありません。

### 修正の観点

1. Node.js 18のサポート終了の記述に、コンテキストにある出典（Node.js Releases）のリンクが添えられている
2. 出典の該当箇所（v18のEnd-of-lifeが「2025-04-30」）が引用されている
3. コンテキストにも元の文書にもないリンクや引用を加えていない
4. 2文目とコードブロックが元のまま残っている

### 合格の例

````markdown
## Node.jsのバージョン

Node.js 18のサポートは2025年4月30日に終了しました。[Node.js Releases](https://nodejs.org/en/about/previous-releases)の一覧表では、v18のEnd-of-lifeが「2025-04-30」です。

次の設定で、Node.js 20以上を必須にしています。

```json
{ "engines": { "node": ">=20" } }
```
````

````markdown
## Node.jsのバージョン

Node.js 18のサポートは2025年4月30日に終了しました。

> v18 … End-of-life: 2025-04-30
>
> 出典：[Node.js Releases](https://nodejs.org/en/about/previous-releases)

次の設定で、Node.js 20以上を必須にしています。

```json
{ "engines": { "node": ">=20" } }
```
````

### 不合格の例

リンクだけを添え、該当箇所を引用していない。

````markdown
## Node.jsのバージョン

Node.js 18のサポートは2025年4月30日に終了しました（出典：[Node.js Releases](https://nodejs.org/en/about/previous-releases)）。
````


## claim-grounds

- ルール：主張には、根拠となる事実と、事実から主張が言える理由を添えます
- 検知する文：このライブラリを採用すべきです

### コンテキスト

- 候補のライブラリは2つで、圧縮後のサイズは、このライブラリが12KB、もう1つが85KBです
- このプロジェクトでは、1ページで読み込むJavaScriptを合計100KB以内にすると決めています

### 変えない文

````text
ビルドが失敗しています。このPRはマージすべきではありません。
````

### 誤りの箇所と理由

「このライブラリを採用すべきです」が誤りです。書き手の判断を述べる主張なのに、根拠となる事実と、事実から主張が言える理由が書かれていないので、読み手は主張を採るかを判断できません。事実（圧縮後のサイズが12KBと85KB）と論拠（1ページのJavaScriptを合計100KB以内にする決まり）はコンテキストにあるので、その事実を使って直せます。2つ目の主張は、ビルドが失敗しているという事実があり、マージすべきでない理由が想定読者にとって1通りに決まるので、違反ではありません。

### 修正の観点

1. 根拠となる事実として、コンテキストにある2つの候補のサイズ（12KBと85KB）が書かれている
2. 事実から主張が言える理由として、1ページのJavaScriptを合計100KB以内にする決まりが書かれている
3. コンテキストにも元の文書にもない事実や数値を加えていない
4. 2つ目の主張が元のまま残っている

### 合格の例

````markdown
## 判断

このライブラリを採用すべきです。圧縮後のサイズは、このライブラリが12KB、もう1つの候補が85KBです。このプロジェクトでは1ページで読み込むJavaScriptを合計100KB以内にすると決めているので、サイズの小さいこのライブラリのほうが、ほかのコードに使える容量が多く残ります。

ビルドが失敗しています。このPRはマージすべきではありません。
````

````markdown
## 判断

このプロジェクトでは、1ページで読み込むJavaScriptを合計100KB以内にすると決めています。候補のライブラリの圧縮後のサイズは12KBと85KBで、85KBのほうを採用すると、ほかのコードに使える容量の大半を1つのライブラリが占めてしまいます。そのため、12KBのこのライブラリを採用すべきです。

ビルドが失敗しています。このPRはマージすべきではありません。
````

### 不合格の例

論拠だけを書き、根拠となる事実（サイズの値）を書いていない。

````markdown
## 判断

このライブラリを採用すべきです。サイズが小さいライブラリのほうが、ページの読み込みが速くなるためです。

ビルドが失敗しています。このPRはマージすべきではありません。
````

コンテキストにない事実を作って書き換えている。

````markdown
## 判断

このライブラリを採用すべきです。過去1年に報告された脆弱性は0件で、月に2回以上リリースされています。脆弱性が報告されておらず、リリースが続いているライブラリは、保守が続くと考えられるためです。

ビルドが失敗しています。このPRはマージすべきではありません。
````

## literal-verb

- ルール：動詞と副詞は文字どおりの意味で使います
- 検知する文：テストを回します

### 変えない文

````text
リリースする前に`npm test`を実行します。
````

### 誤りの箇所と理由

「テストを回します」の「回します」が誤りです。テストを物を動かす動作に例えた比喩的な動詞で、実際に何をするのかが書かれていません。ルールに従って、「実行します」のように実際の動作を表す動詞に書き換えます。2文目の「実行します」は文字どおりの意味なので、違反ではありません。

### 修正の観点

1. 「回します」が残っておらず、テストについて実際の動作を表す動詞（「実行します」など）が使われている
2. マージする前にテストをすることが、元の文から変わっていない
3. 2文目が元のまま残っている

### 合格の例

````markdown
## テスト

マージする前にテストを実行します。

リリースする前に`npm test`を実行します。
````

````markdown
## テスト

テストを実行してから、マージします。

リリースする前に`npm test`を実行します。
````

### 不合格の例

比喩的な動詞が残っている。

````markdown
## テスト

マージする前にテストを走らせます。

リリースする前に`npm test`を実行します。
````

テストをする時点が変わっている。

````markdown
## テスト

マージした後にテストを実行します。

リリースする前に`npm test`を実行します。
````

## concrete-example

- ルール：読み手が思い浮かべにくい内容には、具体例を添えます
- 検知する文：入力値は境界値で検証します

### コンテキスト

- 検証する入力値の1つは注文フォームの数量で、1以上99以下を受け付けます
- 数量のテストでは、0・1・99・100を入力して検証しています

### 変えない文

````text
検証に失敗した入力は保存しません。
````

### 誤りの箇所と理由

「入力値は境界値で検証します」が誤りです。「境界値」の意味は1つに決まりますが、読み手は自分の入力項目のどの値を検証すればよいかを決められません。注文フォームの数量の範囲（1以上99以下）と、検証している値（0・1・99・100）はコンテキストにあるので、その事実を具体例として添えて直せます。

### 修正の観点

1. 「入力値は境界値で検証します」に、読み手が自分の場面に当てはめられる具体例が添えられている
2. 具体例が、コンテキストにある事実（数量は1以上99以下、検証する値は0・1・99・100）で書かれている
3. コンテキストにも元の文書にもない値を加えていない
4. 2文目が元のまま残っている

### 合格の例

````markdown
## 入力値の検証

入力値は境界値で検証します。たとえば注文フォームの数量は1以上99以下を受け付けるので、0・1・99・100を入力して検証します。

検証に失敗した入力は保存しません。
````

````markdown
## 入力値の検証

入力値は境界値で検証します。たとえば、1以上99以下を受け付ける注文フォームの数量では、下限の前後の0と1、上限の前後の99と100を検証します。

検証に失敗した入力は保存しません。
````

### 不合格の例

具体例を添えていない。

````markdown
## 入力値の検証

入力値は、受け付ける範囲の上限と下限の前後の値で検証します。

検証に失敗した入力は保存しません。
````

コンテキストにない値を作って具体例を加えている。

````markdown
## 入力値の検証

入力値は境界値で検証します。たとえば上限が100件なら、99件・100件・101件の3つを検証します。

検証に失敗した入力は保存しません。
````
