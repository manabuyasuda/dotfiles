# x-why-so

文章を命題ごとの行に分け、トゥールミン・モデルの要素として箇条書きに並べます。欠けている情報を埋めてから、書き直し案を示します。採否はユーザーが決めます。

## 要素

| 要素 | 定義 |
|---|---|
| 主張 | 書き手が読み手に受け入れさせたい結論です。 |
| データ | 主張を支えるために示す事実です。読み手が真偽を確かめられる形で書きます。 |
| 前提 | 主張が成り立つ状況を説明する事実です。その行を消しても主張の理由が消えない場合は、データではなく前提に当たります。 |
| 論拠 | データから主張を導いてよいとする、一般的な規則です。文章に書かれないことが多くあります。 |
| 裏づけ | 論拠を支えるために示す事実です。データと同じ種類の事実でも、論拠を支えるものは裏づけに当たります。 |
| 限定条件 | 主張がどの程度確かか、どの範囲で成り立つかを示す語です。独立した行にはせず、主張の行の中に残します。 |
| 例外 | 主張が成り立たなくなる条件です。トゥールミン・モデルの「反駁」に当たります。例外に書くのは、主張への反論に答える文ではなく、主張が成り立たなくなる条件だけです。 |

## 手順

### 1. 構造を書き出す

- 1つの述語で言い切れる命題ごとに1行を作ります。名詞を修飾する節は、修飾される名詞と同じ行にまとめます
- 行の先頭に要素名を書き、支える行を、支えられる行の下に字下げして置きます
- 主張を最上位に置きます。見出しがあれば、見出しから主張を決めます
- データは、そのデータを支えるデータを下に持てます
- データの行は、親の行に対する関係を要素名の後に「（理由）」または「（続き）」で添えます。親の行が成り立つ理由を述べる場合は「（理由）」、親の行の後に起きることを述べる場合は「（続き）」です
- 文末は常体にし、名詞で終わる文は「である」で終えます。否定文は、肯定文に言い換えられる場合だけ言い換えます
- 指示語と省略された語は、原文の別の文にある語で埋め、埋めた語を「【】」で囲みます。原文のどこにもない語は「＿＿」にします
- 「AのB」のように関係が複数に読める語は、関係を表す語で書き、書き足した語を「【】」で囲みます
- 一文の分割、常体への統一、肯定文への言い換えには「【】」を付けません。これらは原文にある情報の書き表し方を変えるだけで、原文が読み手に渡していない情報を補うものではないからです
- 主張を導くのに欠かせない行が原文にない場合は、推測した文を書き、要素名の後に「（原文になし）」と添えます
- 各行は、その行だけを読んで理解できるようにします

出力の例は次のとおりです。

```markdown
- 主張：おそらく、太郎は日本国民である。
  - データ：【太郎の】父は、太郎が生まれたときに日本国民だった。
  - 論拠（原文になし）：生まれたときに父または母が日本国民である子は、日本国民である。
    - 裏づけ：国籍法第2条が、生まれたときに父または母が日本国民である子を、日本国民と定めている。
  - 例外：太郎が国外で生まれて外国の国籍も得ており、日本の国籍を留保する届を出していない場合は、日本国民ではない。
```

### 2. 欠けを埋める

「＿＿」と「（原文になし）」の行を、1つずつ次の順で扱います。

1. リポジトリのコードと設定、公式ドキュメントで確かめられるものは、エージェントが調べて埋めます
2. 調べて確かめられないものは、x-grillingでユーザーに質問して埋めます
3. 質問しても埋まらないものは、その行を消すか、主張を変えるかをユーザーに決めてもらいます

原文、調査結果、回答にある情報だけで埋めます。すべての欠けを解消してから、次の手順に進みます。

### 3. 確からしさを検討する

主張ごとに、次の5つの基準で支えが足りているかを確かめます。

| 基準 | 確かめること |
|---|---|
| 関連性 | データが、主張の真偽に関係しているか |
| 確かさ | データが、観察や出典で確かめられるか |
| 十分さ | データの量と種類が、主張の強さに見合っているか |
| 論拠 | データから主張を導く論拠が受け入れられ、必要な裏づけがあるか |
| 例外 | 主張が成り立たない条件を検討し、限定条件で主張の範囲を絞っているか |

基準を満たさない箇所は、x-grillingでユーザーと検討します。データを足すか、限定条件で主張を弱めるか、主張を消すかを決めます。すべての主張の確からしさをユーザーが十分と判断したら、次の手順に進みます。主張のない文章（手順や事実の説明など）では、この手順を省きます。

### 4. 構造を保存する

構造を対象のファイルと同じディレクトリに`<対象のファイル名から拡張子を除いた名前>.why-so.md`として保存し、パスをユーザーに伝えます。対象が`docs/plan.md`であれば、保存先は`docs/plan.why-so.md`です。

ファイルの先頭に次の2行を記述して対象外にします。

```markdown
<!-- textlint-disable -->
> 一時的に作成しているファイルです。校正は禁止です。
```

### 5. 書き直し案を示す

手順1で書き出した構造を、次の規則で文章へ変換します。規則は構造だけを入力とするため、原文が主張を含むか、表や箇条書きを含むか、見出しを持つかにかかわらず適用できます。

#### 5-1. 段落を作る

1. 構造の最上位にある行1つにつき、段落を1つ作ります。最上位の行の要素名（主張・データなど）にかかわらず、同じように扱います
2. 段落の先頭文を、最上位の行にします
3. 最上位の行を支える行を、親の行の直後に、深さ優先で置きます。同じ親を持つ行が複数ある場合は、手順1で書き出した順序を保ちます
4. 限定条件は、独立した文にするのではなく、主張の行の中に残します
5. 例外の行は、規則3の順序から外し、段落の末尾に置きます
6. 段落の間は1行空けます

#### 5-2. 論拠を書くかを決める

7. 本文には、ユーザーが書くと決めた論拠と、その裏づけだけを書きます。ユーザーが手順3の「論拠」の基準を満たさないと判定した論拠は、本文から省きます
8. 論拠を書く場合は、その論拠が支えるデータの直後に置き、裏づけを論拠の直後に置きます

#### 5-3. 文末の形で関係を示す

9. 行の種類に応じて、次の表の文末の形を使います。文頭の接続表現は、例外の行にだけ書きます

| 行の種類 | 文末の形 |
|---|---|
| 主張 | 〜です、〜ます（言い切ります） |
| 前提 | 〜です、〜ます（言い切ります） |
| データ（理由） | 〜からです、〜ためです |
| データ（続き） | 〜です、〜ます（言い切ります） |
| 親と同じ内容を言い換えた行 | 〜ということです |
| 例外 | ただし、〜場合は〜してよいことにします |

10. 1つの段落で「〜からです」を使うのは最初の1回だけにし、2回目以降の「データ（理由）」の行は言い切ります。段落のどこで根拠が始まるかは1回示せば、続く行も根拠だと読み手に伝わるためです

#### 5-4. 命題に分解できない要素を扱う

11. 表・箇条書き・コードブロック・図は、構造の行にするのではなく、原文の形式と位置のまま残します
12. 残した要素の直前に、その要素が何を示すかを1文で書きます。その1文を構造の行として扱います

規則12の1文は、文書ごとに書き分けます。要素を読む前に渡すべき注意点が文書ごとに異なるため、定型文にすると案内しか書けなくなってしまいます。

#### 5-5. 文書全体を組み立てる

13. 原文に見出しがある場合は、見出しとその階層をそのまま残し、見出しの配下ごとに5-1から5-4を適用します
14. 本文を直接持つ見出しの直下に、その配下の内容を1文で書きます。下位の見出しだけを持つ見出しには、1文を書きません
15. 段落と見出しの順序は原文のまま保ちます。順序を変えるのは、5-6の完了条件を満たさず、ユーザーが並べ替えに同意した場合だけにします
16. 文末を原文の文体に戻します。手順1では構造を常体に統一しているため、原文が敬体である場合は敬体へ戻します。原文で常体と敬体が混在している場合は、敬体に統一します。常体だけで書かれた原文は、常体のまま残します。規則9の表は敬体で示しているため、原文が常体である場合は「〜からだ」「〜ということだ」のように常体へ置き換えます

#### 5-6. 完了条件

次の5つをすべて満たすまで書き直します。

- 書き直した本文に手順1を適用した場合に、「【】」「＿＿」「（原文になし）」が1つも出ない
- 段落の数が、構造の最上位にある行の数と、規則12と規則14で足した1文の数の合計と一致する
- 規則12と規則14で足した1文を除いた各段落の先頭文が、構造の最上位の行と1対1で対応する
- 段落の先頭文だけを順に並べた場合に、原文の要約として筋が通る
- 表・箇条書き・コードブロックのすべてに、直前の1文がある

5つすべてを満たす場合は、原文のままでよいことをユーザーに伝えます。1つでも満たさない場合は書き直します。

書き直し案と、変更点ごとの理由をユーザーに示します。採用するかはユーザーが決めます。原文のファイルはそのまま残します。
