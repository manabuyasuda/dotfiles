# x-commit

x-commitスキルは、Gitコミットを論理単位の粒度で作成します。コミットメッセージには、履歴を読む人（自分・他人・AI）へ変更の理由を伝える記述を書きます。

`commit-message-writer`サブエージェントは、コミット計画を提案します。そのために、Gitの状態を把握し、規約を確定し、変更した理由を収集します。x-commitスキルは、ユーザーの承認を受け取ります。そのあと、計画どおりにGitを操作します。

## ワークフロー

### Step 1: commit-message-writerでコミット計画を作成する

`commit-message-writer`サブエージェントを起動し、「コミット計画を作成してください」と伝えます。ユーザーの元の依頼に、計画へ反映する条件が書かれている場合は、その記述を`commit-message-writer`への依頼に含めます。計画へ反映する条件とは、scope（コミットメッセージに書く、変更した範囲を表す語）の指定・分割の方針・関連するissue番号です。

`commit-message-writer`が返す計画は、対象ファイルとメッセージ全文を含みます。

### Step 2: 計画を提示して承認を得る

`commit-message-writer`から返ってきた計画の末尾に、以下の確認文を付けます。その計画をそのままユーザーへ提示します。

```
この計画でコミットしてよいですか？修正点があれば指示してください。
```

ユーザーから修正指示があった場合は、その指示を添えて`commit-message-writer`へコミット計画の作成を再依頼します。そのあと、Step 2を繰り返します。

### Step 3: 承認後、計画どおりに実行する

承認を得た場合は、計画に書いたすべてのコミットを、途中でユーザーへ確認せずに続けて作成します。

1. ステージング状態を計画に合わせます。`git reset`で、`git reset`を実行する前のステージング状態をクリアします。そのあと、`git add -A -- <files>`で計画どおりのファイルだけをステージングします。`git reset`はワーキングツリーのファイルを変更しません
   - `-A`を使うのは、`git mv`でファイル名を変更した場合に、変更前のファイルの削除もステージングするためです
2. コミットメッセージの全文を書き込んだファイルを1つ作り、`git commit -F <ファイル>`で実行します。ファイルはリポジトリの外に作ります
   - `-m`を使わないのは、メッセージに含まれるバックティックや`$`をシェルが展開してしまうためです
   - ファイルをリポジトリの外に作るのは、`git status`に未追跡ファイルとして現れるのを防ぐためです

完了後は`git log -n <作成したコミット数> --oneline`の結果を提示します。エラーで中断した場合は、作成できたコミット・失敗したコミット・まだ作成していないコミットを区別して報告します。

#### エラー時の挙動

| 状況 | 対応 |
|------|------|
| pre-commit hook（コミット作成の直前にGitが実行する検査・整形スクリプト）による自動修正 | pre-commit hookが書き換えたファイルを`git add`で再度ステージングします。そのうえで再コミットします |
| commitlint（コミットメッセージが規約に沿っているか検査するツール）の違反 | エラー出力を読んでメッセージを修正します。そのあと、1回だけ再試行します。2回目も失敗した場合は、エラー内容とメッセージ案をユーザーへ伝えます。そのあとは、ユーザーの指示を待ちます |
| pre-commit hookの失敗やテストの失敗のような、自動修正とcommitlint違反のどちらにも当てはまらないエラー | 残りのコミットを作成せずに実行を中止します。発生したエラーの内容を報告します。次に何をするかは、ユーザーに決めてもらいます |

## Git操作の制約

- `git commit`は`--no-verify`を付けずに実行します。pre-commit hookとcommitlintによる検査が実行されます
- `git push`は、ユーザーが依頼したときだけ実行します
- `git commit --amend`と`git rebase`は、ユーザーが依頼したときだけ実行します
