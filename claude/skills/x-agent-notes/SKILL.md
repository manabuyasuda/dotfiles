# x-agent-notes

AIエージェントが作業をしたログと判断とその根拠、ユーザーの最終判断から、エージェントに渡す推奨パターンを作成します。
信頼性がありトークン効率の高い処理をエージェントにさせることが目的です。

作業ログの場所と抽出処理は実行エージェントごとに異なるため、スクリプトを差し替えます。それ以外の手順は共通です。
対応表は次のとおりです。

| 実行エージェント | スクリプト | ログの場所 |
|---|---|---|
| Claude Code | `scripts/claude-log-summary.sh` | `~/.claude/projects/<cwd-slug>/*.jsonl` |
| Codex | `scripts/codex-log-summary.sh` | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` |
| Cursor | `scripts/cursor-log-summary.sh` | `~/.cursor/chats/<cwdのMD5ハッシュ>/<セッションID>/store.db` |

## Step 1: 対象範囲を特定する

1. `git rev-parse --show-toplevel`でgitルートを取得します
2. ユーザーに対象範囲（どの作業のログを対象にするか）を質問します。「この作業」「今日の作業」「日時の指定」「ログ全体」のような回答を受け取ります。
3. 冒頭の対応表から、スクリプトとログの場所を確認します。そのスクリプトに`--section files`とユーザーの回答を読み替えた引数を付けて実行し、対象ログファイルの一覧を確認します。読み替えは次のとおりです。
   - 日時で指定された場合は、epoch秒に変換して`--cwd <gitルート> --since <epoch>`を渡します
   - 「この作業」のように現在の会話を指す場合は、現在のセッションのログファイルを`--file`で渡します
   - ログ全体の場合は`--cwd <gitルート>`だけを渡します

対象ファイルが0件の場合は、その旨をユーザーに伝えて対象範囲を選び直してもらいます。

## Step 2: ログの要約を取得する

同じスクリプトを`--section utterances,tools,failures,tokens`で実行します。

- 参照するのは要約のみとします。ログ本体（transcript JSONLやrollout JSONL）を読むとかえってコンテキストが膨らむためです
- 詳細が必要になった場合だけ、`--file <対象ファイル>`と`--section`で範囲を絞って追加取得します

## Step 3: 5分類の案を提示して確認を得る

要約をもとに、記録候補を5分類に仕分けた案を作ってユーザーに提示します。判定の目安は次のとおりです。

| 分類 | ディレクトリ | 判定の目安 |
|---|---|---|
| 最初からうまくいった | `worked-first-try/` | エージェントの応答のあとに、ユーザーの修正指示もエージェントの再試行も入らずに次の作業へ進んでいる区間です |
| 試行錯誤でうまくいった | `worked-after-retry/` | ユーザーの指示なしに、エージェントが別の方法に変更して再試行し、最終的に通った区間です。試した順に方法を残します |
| ユーザーの指示でうまくいった | `worked-with-guidance/` | ユーザーの発言を挟んでやり直している区間です。やり直し直前のユーザーの発言を指示の内容として拾います |
| 失敗した | `failed/` | ユーザーが止めた、エージェントが別の方法に変更して再試行しても解決に至らなかった、コマンドが失敗した、の3つを区別します |
| 繰り返し調べている | `recurring-lookups/` | ツール呼び出し（ファイル読み取り・検索・外部参照）の対象別回数から、繰り返し参照している構造や仕様を拾います |

提示は候補ごとに「分類・タイトル案・根拠（要約のどの行から判断したか）」を1行ずつ並べ、ユーザーが取捨選択と修正のできる形にします。ファイルへの書き込みはユーザーの確認を得てから行います。

## Step 4: 承認された内容をwiki/agent-notes/へ記録する

1. 記録先は`<gitルート>/wiki/agent-notes/<分類ディレクトリ>/<kebab-caseの名前>.md`です。ディレクトリがなければ作成します。
2. 本文の先頭に次の3項目を書き、そのあとに根拠となるデータや情報（実際のコマンド・出力・判断の経緯）を続けます
   - 「目的」には、何を達成したいときに開くノートかを、満たしたい要求で書きます（例:「エージェントへの質問ではなく、ログに残った事実をもとに作業の経過を判断したいとき」）。参照するファイルや手段は結果なので「対象」と「方法」に書きます
   - 「対象」には、扱うファイルのパス・コマンド・データ構造を具体名で書きます（例:「`~/.codex/sessions/`配下の`session_meta`レコード」）
   - 「方法」には、エージェントがそのまま実行できるコマンドや手順と、結果をどう判定するかの基準を書きます
3. 次回のエージェントが本文だけで再現できる分量に絞ります。作業の経緯の網羅ではなく、再利用できるパターンの記述を優先します

## Step 5: index.mdを更新する

1. Step 4で記録した本文から、キーワード（対象の名前・技術用語・コマンド名・パスなど、エントリを探すときの手がかりになる語）をピックアップします
2. キーワードを踏まえて、エントリのタイトルを考えます
   - タイトルには記録ファイルへの相対パスのmarkdownリンクをつけます
   - タイトルには、Step 4の本文の先頭3項目（目的・対象・方法）を要約した1文にします。例は「`[作業ログの事実から経過を判断するためにCodex rollout JSONLのレコード構造をjqで抽出する](recurring-lookups/codex-rollout-jsonl-structure.md)`」です
   - ピックアップしたキーワードは、言い換えずにそのままの形でタイトルに含めます。
3. エントリのステータスはユーザーが決めます。確定とWIPのどちらにするかをユーザーへ質問し、あわせてタイトルの案を確認してもらいます
4. 確定した内容を`<gitルート>/wiki/agent-notes/index.md`に1件1行・「タイトル・ステータス」の2列で追記します。index.mdが存在しない場合は、分類表とステータス定義を含む索引を新規作成します

確定（この通りにやればもっとも効率的だと判断できる状態）への昇格は、同様のパターンが繰り返し成功した場合にユーザーへ提案し、承認を得てから変更します。
